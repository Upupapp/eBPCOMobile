## T-01 · Four subsystems are built, tested, and never called — HIGH

Each of these exists with tests and is referenced by nothing outside its own
file:

| Class | References in `lib/` |
|---|---|
| `CertificatePinner` | 1 — its own file |
| `SessionManager` | 2 — its own file, and a *comment* in `session_cleaner.dart` |
| `SyncEngine` | 1 — its own file |
| `OfflineQueue` | 2 — its own file, and `SyncEngine`, which is itself unreached |

`ApiClient` holds a plain `http.Client`: no pinner, no
`badCertificateCallback`, no `SecurityContext`. **So there is no certificate
pinning in effect.** `SyncEngine` is what drains the offline queue, so a
queued submission would sit there.

This is very likely deliberate staging — pinning needs the real host's
certificate, and a sync engine needs something to sync to, neither of which
exists yet. Both ADRs are careful and well-argued. **But neither says the code
is not yet wired, and nothing else in the repo does either.**

That matters most for pinning. A security control that is present in the
source and not in effect is worse than one that is absent: a reader, a
reviewer, or an auditor concludes the app is protected. Absent code invites
the question; dormant code answers it wrongly.

Fix: say so where it will be read — a line in each ADR and a `// Not yet
wired: see M-##` at each class — or wire what can be wired now. This is the
Android/Windows lane's code; the iOS lane raising it, not changing it.

## T-02 · The wizard progress header is copied sixteen times — FIXED

`_WizardProgressHeader` is defined once per wizard screen: fourteen with
byte-identical bodies once string literals are normalised, two with small
variants.

The cost is already paid rather than hypothetical. Fixing the 200% text-scale
overflow in S-06 meant a scripted edit across all sixteen; a shared widget
would have been one edit and one place to get wrong.

**Fixed 19 Aug 2026.** Extracted to
`lib/shared/widgets/layout/wizard_progress_header.dart`, parameterised on the
intro line. Net −1038 lines across the sixteen screens.

The duplication had already produced a real inconsistency, found while doing
this. The two variants differed only in how one string wrapped across source
lines, and that was enough for the scripted S-06 `maxLines` fix to miss both —
so Excavation and Certificate of Occupancy never received the bounding the
other fourteen did. They passed the accessibility suite anyway because the
title and subtitle bounding carried them. Extraction closed it for all sixteen
at once.

The extraction also went wrong before it went right: the first attempt
truncated each file at the header class, which deleted `_BottomActionBar`
below it in every wizard. `flutter analyze` caught it immediately; the redo
removes exactly one brace-balanced class block. Worth recording because "cut
from here to end of file" looked safe and was not.

The shared widget now has its own test, since sixteen screens depend on it,
and gained a semantics label — a progress bar is invisible to a screen reader
without one, and none of the sixteen copies had it.

## T-03 · The commencement threshold is stated twice — FIXED, and it was mine

`NotificationEvaluator.commencementWarningDays = 60` carries a comment saying
it "matches the Home action stack, so the two cannot disagree about what
'soon' means". `ActionItemBuilder` hardcodes `daysLeft <= 60` on its own.

They agree today by coincidence, and my comment claims a guarantee the code
does not provide.

**Fixed 19 Aug 2026.** `ApplicationModel.commencementWarningDays` is the one
home, beside `commenceByDate` — the rule it serves. Both consumers read it.

Related, though not duplication: `prcNeedsAttention` warns at 60 days and
`SavedDocumentModel.needsAttention` at 30. Both are deliberate and reasoned in
their own files, but there is no one place a reader can see the app's
warning thresholds together.

## T-04 · `flutter_svg` is declared and never used — FIXED

No import anywhere in `lib/` or `test/`, and no `.svg` in `assets/`.

Worth removing rather than leaving: every dependency is compiled for both
platforms and can raise an OS floor as a side effect, which is exactly how the
iOS floor moved to 15.0 in S-04. A package that does nothing should not be
able to do that.

**Removed 19 Aug 2026.**

## T-05 · Accessibility still covers 3 screens plus the wizards — FIXED

S-06 added the sixteen wizards and all sixteen shared widgets. The screen-level
suite still named only `DashboardScreen`, `NotificationsScreen`, and
`CitizensCharterScreen`.

**Fixed 19 Aug 2026.** `test/accessibility_screens_test.dart` covers the seven
that were missing — `ApplicationListScreen`, `ApplicationDetailScreen`,
`OrderOfPaymentScreen`, `PaymentHistoryScreen`, `ProfessionalsScreen`,
`PreFlightScreen`, `PrivacyDataScreen` — at 100%, 200% text scale, 320dp, and
against the 48dp touch floor. 28 cases.

The prediction in the original entry held: composition was where the defects
were. Four failed on first run, and one of them fails at **normal text size on
a 320dp phone**, which is a shipping bug rather than an accessibility edge.

### Two defect families, five sites

**Money rows.** `Expanded(label)` beside an unbounded amount `Text`. `Row`
lays the unbounded child out first at its natural width and hands `Expanded`
the remainder — which at 200% was three and a half pixels, so the label
overflowed. Ellipsising is not the fix: these are fee names and centavo
amounts on a document the applicant pays against, and money must never be
truncated.

Extracted `lib/shared/widgets/layout/amount_row.dart`, which reflows the
amount onto its own line instead of shrinking either side. A `Wrap` makes that
decision, so there is no text-scale threshold to get wrong — the amount moves
exactly when it does not fit, at any scale and any width. Four call sites
across the two payment screens.

**Status pills.** `StatusBadge` has existed in `lib/shared/widgets/badges/`
the whole time. Five sites hand-rolled it anyway, and all five put the pill in
a `Row` as an unbounded sibling of an `Expanded` title — the same shape, the
same failure. The hand-rolled copies also lacked the
`Semantics(label: 'Status: …')` the shared widget carries, so every one of
them was a status invisible to a screen reader.

Replaced with `Flexible(StatusBadge(...))`, which is what
`shared/widgets/cards/tracking_card.dart` already did and why that card never
failed.

Only two of the five were caught by the new screen tests. The other three
passed because the fixture's status labels happened to be short enough — they
are latent, not absent. That is why the fix came with
`test/architecture/status_badge_usage_test.dart`, which scans `lib/features`
for the shape rather than waiting for a fixture long enough to trip it. It
flags 4 sites at the pre-fix commit and none now.

Also worth recording: `dart format lib/` reformatted ~230 files, most of them
the Android lane's, because the repo is not formatted to the current
`dart format` style. Format single files, never the tree.

## T-06 · The other twenty-three routable screens — FIXED

T-05 covered the seven the sweep named. This covered what was left that a user
can actually reach: the five authentication and first-run screens, five more
application screens, the three business screens, documents, payments, and the
eight profile and settings screens.

`test/accessibility_routes_test.dart`, 92 cases. Unlike T-05's suite it runs
the app's own mock repositories and real providers — the same objects
`app.dart` wires up — because T-05 ended with three latent defects that a
hand-built fixture was too short to trip. Here the data is the seed data.

Four defects, and again the worst of them fail at **normal text size on a
320dp phone** rather than only at 200%.

| Screen | Defect |
|---|---|
| `ApplicationsScreen` | `GridView(mainAxisExtent: 214)` — 8px bottom overflow |
| `ApplicationsScreen` | `BeforeYouStartCard` heading — 10px right overflow |
| `LoginScreen` | "Remember me" / "Forgot password?" — 15px right overflow |
| `ChangePasswordScreen` | password requirement rows — 116px right overflow |

### The same story a third time

`ResponsiveCardGrid` exists in `lib/shared/widgets/layout/`. Its doc comment
says in as many words that it was written because `GridView`'s fixed cell
sizing overflowed the dashboard's cards on real Android devices at raised font
sizes. `ApplicationsScreen` used a raw `GridView` with a hardcoded
`mainAxisExtent: 214` and overflowed by 8px at 320dp. Two screens needed the
fix; one had it.

That is now three of these in two passes — `WizardProgressHeader` copied
sixteen times (T-02), `StatusBadge` hand-rolled five times (T-05), and
`ResponsiveCardGrid` adopted by one screen of two. The pattern is not that the
shared widget is missing; it is that nothing tells the next author it exists.
Hence a second guard, `test/architecture/fixed_height_grid_test.dart`, which
fails on any pinned cell height in `lib/features`. It flags the applications
screen at the pre-fix commit and nothing now.

`BeforeYouStartCard` is the same shape in miniature: `_ChecklistRow` in that
very file wraps its text in `Expanded`, and the heading Row eight lines above
it did not.

### `ReflowingRow`

The Login fix needed what `AmountRow` does — two items at opposite ends that
must move onto separate lines rather than shrink — for a checkbox and a text
button rather than money. Rather than copy the `Wrap`, the implementation
moved to `lib/shared/widgets/layout/reflowing_row.dart` and `AmountRow` is now
a four-line specialisation of it that keeps the money-specific rationale where
a reader will find it.

### Still uncovered, deliberately

Fourteen `…ApplicationSubmittedScreen` variants, `SplashScreen`, and
`DocumentPreviewScreen`. The submitted screens are near-identical confirmation
pages and are better served by one shared-widget test than fourteen screen
tests; that is worth doing but is a different job from this one.

## T-07 · The last sixteen screens, and consolidating them — FIXED

The sixteen terminal confirmation screens plus splash and document preview
were the remainder. `test/accessibility_terminal_screens_test.dart`, 72 cases,
same four checks.

**All 72 passed on the first run.** These screens are centred columns inside
`FormScrollScaffold`, and the doc comment on each says that scaffold was
chosen precisely so the content scrolls instead of overflowing on short
viewports. It worked. Worth recording as the one place the codebase had
already solved this before being asked.

Every screen class in `lib/features` — 67 of them — now appears in an
accessibility suite.

### Consolidation

With the suite green as a safety net, fifteen of the confirmation screens
moved onto a shared
`lib/features/applications/presentation/widgets/application_submitted_view.dart`.
**425 lines replacing 2,106.**

They were copies, and the copying had already cost something. Three headlines
said "… Permit Submitted!" where twelve said "… Application Submitted!" — and
the three were wrong on the facts, since what an applicant submits is an
application, not a permit. Normalised, and three wizard tests updated to
match. Body copy also alternated between "Your Plumbing Permit application"
and "Your demolition permit application" with no rule behind it; preserved as
found rather than folded in, since that is a copy decision rather than a
defect.

### What consolidation nearly broke, and what it disproved

Two things are worth recording more than the line count.

**A near-miss caught by the tests.** Certificate of Occupancy renders an
"Application Status" sequence below its summary card that no other screen has.
The parser used to drive the rewrite only looked for `_InfoRow`, so it never
saw that section and the rewrite deleted it. `certificate_of_occupancy_wizard_test`
failed within one run. The shared view gained an `extra` slot. Writing the
coverage before the refactor is what made that a five-minute fix instead of a
silent regression.

**A defect that turned out not to be one.** The parse showed
`ArchitecturalApplicationSubmittedScreen` gating its notice on
`relatedBuildingPermitStatus != 'Issued'` where the other thirteen use
`!= 'Approved'` — which reads exactly like drift. It is not. Architectural has
its own `RelatedBuildingPermitStatus` enum whose members are `pendingIssuance`
and `issued`, so `'Issued'` is the correct string there and `'Approved'` would
have broken it. Two same-named enums in different model files, with different
members. Had the notice text been centralised on the assumption they agreed —
which was the obvious consolidation — three screens would have started telling
applicants something false.

`test/architecture/submitted_screen_usage_test.dart` is the third guard, and
keeps a sixteenth permit type from starting the cycle again.

## T-09 · The text-scale clamp, and what it was hiding — FIXED

`app.dart` clamped system font scaling to a maximum of 1.3x. Someone who set
their phone to 200% because they need 200% got 130%, on every screen.

The comment was honest about why: layouts were built against a 1.0x desktop
preview and overflowed on real Android phones with the font size raised, so
the scale was capped instead. It named three culprits — "the 5-item bottom nav
bar, status badge pills, fixed-height cards". By this point the pills were
fixed and guarded (T-05) and the fixed-height cards were fixed and guarded
(T-06). The nav bar had never been looked at, and had no test at all.

**It was clipping.** At 2.0x on a 320dp screen, "Applications" ran 4dp past the
bottom of the bar. `NavigationBar` pins itself to `height: 88` here and clips
rather than reporting an overflow — so six render tests at 1.0x, 1.3x and 2.0x
all passed while the label was being cut off. Only asserting the label's rect
against the bar's rect caught it.

That is the lesson worth keeping from this one, and it is the second time the
same lesson has come up: **a test that only asks "did anything overflow?"
cannot see clipping.** The bar now grows with the text scale, bounded at 2x.

With that fixed the clamp went to 2.0, and moved out of a builder literal in
`app.dart` into `lib/core/theme/text_scale_clamp.dart`, where the ceiling is a
named constant with the reasoning beside it. `TextScaleClamp.maxScale` is
deliberately the same number the accessibility suites assert at, and a test
says so — the app should not promise a scale nothing has rendered at, nor
withhold one everything has.

A sweep for other fixed heights that could clip scaled text found two
candidates. `EmptyState`'s 72dp circle holds an icon, and icons do not scale
with the text scaler. The application list's 44dp segment strip does hold
text, and was measured rather than assumed: the chip labels are 31dp at 2.0x
and fit. Neither needed changing.
