# Front-end sweep, third pass — 24 August 2026

State and lifecycle: disposal, listener balance, and work that outlives the
widget or provider that started it. Findings are `U-##`.

The first pass looked for gaps against the specification, the second for code
that exists but does not run. Neither looked at *time* — what happens when an
async operation finishes after the thing that started it is gone. That is the
one layer left, and it is where the pass found its defect.

## U-01 · Thirty-nine uploads could `setState` on a dead widget — FIXED

Every upload slot in every wizard does the same thing:

```dart
final result = await showAttachDocumentOptions(context, label: 'PRC ID');
if (result == null) return;
setState(() => _professional.prcIdUpload = result);
```

Thirty-nine of them never checked `mounted` between the `await` and the
`setState`. The analyzer does not catch this: `use_build_context_synchronously`
watches `BuildContext` across async gaps, not `setState`, and there is no lint
for the latter.

**It is reachable, and it was reproduced rather than assumed.** The chooser
leads to the camera, the gallery, or the system file picker — separate Android
activities, any of which can cause the one underneath to be torn down while
open. Mount the step, open the picker, unmount the step, then let the picker
return, and Flutter throws:

```
setState() called after dispose(): _Step5ProfessionalInChargeState#1faf6
  (lifecycle state: defunct, ...)
```

Fixed at all thirty-nine sites with a `mounted` check.
`test/features/applications/lifecycle/upload_after_unmount_test.dart`
reproduces the sequence on one representative slot; it was confirmed to fail
against the unguarded code before being kept, so it is not a test that passes
either way.

## U-02 · Disposal is clean — NOT A DEFECT

A scan for undisposed `TextEditingController`, `ScrollController`,
`PageController`, `AnimationController`, `TabController`, `FocusNode`,
`StreamController`, `Timer` and `StreamSubscription` across 130 classes
returned 148 apparent leaks. **All 148 were false positives**, and the way they
were false is worth recording so the next scan is not re-run from scratch:

- The three large `step4_installation_details.dart` files hold between 30 and
  80 controllers each and account for most of the list. Each creates every one
  through a single `_bind()` helper that registers it in a `_controllers` list,
  and disposes the list in a loop. There is exactly one `TextEditingController(`
  call per file, inside `_bind`, so nothing can escape the registrar.
- `AppTextField.controller`, `AppPasswordField.controller` and
  `_UtilityCard`'s two controllers are constructor parameters. They belong to
  the caller, and disposing them in the receiver would be the bug.

Also checked and clean: `addListener`/`removeListener` balance across the whole
of `lib` (every file balances), the single `Timer` in the codebase
(`AppSearchField`'s debounce, cancelled in `dispose`), and every `dispose()`
override calling `super.dispose()`.

## U-03 · Providers notify after `await` without a disposed guard — SAFE TODAY, NOW ASSERTED

Nineteen async provider methods across `ApplicationsProvider`,
`AuthProvider`, `BusinessProvider`, `DocumentsProvider` and
`NotificationsProvider` call `notifyListeners()` after an `await`, and none
checks whether the provider has been disposed. No provider carries a disposed
flag, and none overrides `dispose()`.

This is **not** a defect today, for one reason: every `ChangeNotifierProvider`
in the app is created in `app.dart`, at the root. Nothing else in `lib`
constructs one. So a provider is only ever disposed when the app itself goes
away, and a late `notifyListeners()` cannot land on a disposed instance.

The reason is a property of the tree rather than of the providers, which makes
it exactly the kind of thing that stops being true without anyone noticing. The
first provider scoped to a route or a screen makes all nineteen sites live at
once: navigate away mid-load, the provider is disposed, the repository answers,
`ChangeNotifier` throws.

So the invariant is asserted rather than assumed —
`test/architecture/provider_scope_test.dart` fails if a provider is created
anywhere but `app.dart`, and says in its failure message what to do about it.
