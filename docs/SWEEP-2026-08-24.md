# Front-end sweep, third pass — 24 August 2026

State and lifecycle: disposal, listener balance, and work that outlives the
widget or provider that started it. Findings are `U-##`.

The first pass looked for gaps against the specification, the second for code
that exists but does not run. Neither looked at *time* — what happens when an
async operation finishes after the thing that started it is gone. That is the
one layer left, and it is where the pass found its defect.

## U-01 · Thirty-nine uploads could `setState` on a dead widget — FIXED

Every upload slot in every wizard does the same thing:

```dart
final result = await showAttachDocumentOptions(context, label: 'PRC ID');
if (result == null) return;
setState(() => _professional.prcIdUpload = result);
```

Thirty-nine of them never checked `mounted` between the `await` and the
`setState`. The analyzer does not catch this: `use_build_context_synchronously`
watches `BuildContext` across async gaps, not `setState`, and there is no lint
for the latter.

**It is reachable, and it was reproduced rather than assumed.** The chooser
leads to the camera, the gallery, or the system file picker — separate Android
activities, any of which can cause the one underneath to be torn down while
open. Mount the step, open the picker, unmount the step, then let the picker
return, and Flutter throws:

```
setState() called after dispose(): _Step5ProfessionalInChargeState#1faf6
  (lifecycle state: defunct, ...)
```

Fixed at all thirty-nine sites with a `mounted` check.
`test/features/applications/lifecycle/upload_after_unmount_test.dart`
reproduces the sequence on one representative slot; it was confirmed to fail
against the unguarded code before being kept, so it is not a test that passes
either way.

## U-02 · Disposal is clean — NOT A DEFECT

A scan for undisposed `TextEditingController`, `ScrollController`,
`PageController`, `AnimationController`, `TabController`, `FocusNode`,
`StreamController`, `Timer` and `StreamSubscription` across 130 classes
returned 148 apparent leaks. **All 148 were false positives**, and the way they
were false is worth recording so the next scan is not re-run from scratch:

- The three large `step4_installation_details.dart` files hold between 30 and
  80 controllers each and account for most of the list. Each creates every one
  through a single `_bind()` helper that registers it in a `_controllers` list,
  and disposes the list in a loop. There is exactly one `TextEditingController(`
  call per file, inside `_bind`, so nothing can escape the registrar.
- `AppTextField.controller`, `AppPasswordField.controller` and
  `_UtilityCard`'s two controllers are constructor parameters. They belong to
  the caller, and disposing them in the receiver would be the bug.

Also checked and clean: `addListener`/`removeListener` balance across the whole
of `lib` (every file balances), the single `Timer` in the codebase
(`AppSearchField`'s debounce, cancelled in `dispose`), and every `dispose()`
override calling `super.dispose()`.

## U-03 · Providers notify after `await` without a disposed guard — SAFE TODAY, NOW ASSERTED

Nineteen async provider methods across `ApplicationsProvider`,
`AuthProvider`, `BusinessProvider`, `DocumentsProvider` and
`NotificationsProvider` call `notifyListeners()` after an `await`, and none
checks whether the provider has been disposed. No provider carries a disposed
flag, and none overrides `dispose()`.

This is **not** a defect today, for one reason: every `ChangeNotifierProvider`
in the app is created in `app.dart`, at the root. Nothing else in `lib`
constructs one. So a provider is only ever disposed when the app itself goes
away, and a late `notifyListeners()` cannot land on a disposed instance.

The reason is a property of the tree rather than of the providers, which makes
it exactly the kind of thing that stops being true without anyone noticing. The
first provider scoped to a route or a screen makes all nineteen sites live at
once: navigate away mid-load, the provider is disposed, the repository answers,
`ChangeNotifier` throws.

So the invariant is asserted rather than assumed —
`test/architecture/provider_scope_test.dart` fails if a provider is created
anywhere but `app.dart`, and says in its failure message what to do about it.

## U-04 · The clipping blind spot, generalised — NO NEW DEFECTS

The nav bar defect (M-41) was invisible to every test in the suite. It did not
overflow a `Flex`, so nothing threw; the label just extended past the box
pinned around it and got cut off in the paint. `expect(tester.takeException(),
isNull)` — the assertion all 200-odd accessibility cases rest on — cannot see
that shape at all.

One defect found by one hand-written geometry assertion says nothing about how
many others are out there. So the assertion was generalised into
`test/support/clipping.dart` and pointed at everything already covered.

**It found nothing new.** 134 new cases across 64 screens, 16 wizards and the
shell, at 1.0x and 2.0x, and the nav bar remains the only place this ever
happened. That is a real result rather than an absent one: the blind spot is
now measured rather than assumed, and it is measured as empty.

The check was validated against the known defect before being trusted. With the
nav bar fix reverted it reports, precisely:

```
MainShell: "Applications" needs 4.0dp more than its NavigationBar(height: 88.0)
allows (text 862.0–904.0, box 812.0–900.0)
```

It also confirmed it is not vacuous: 110 real (fixed box, text) pairs are
examined across the screen suites, so the groups are exercising something
rather than finding nothing to look at.

### What it checks, and what it does not

**Height only, deliberately.** A fixed-height box holding a horizontally
scrolling list is normal and correct — the application list's segment strip is
one — and its content is meant to run off the sides. Content *taller* than the
box it is pinned inside is never correct, because no amount of scrolling
reveals it.

It knows four kinds of box: `SizedBox` with a height, `Container` with a tight
height, `NavigationBar` with a height, and `AppBar`. `AppBar` was added on
suspicion — it pins itself to 56dp and that does not grow with the text scale —
and then measured: Material keeps the title to one line and ellipsises
horizontally, so at 2.0x a title is 37dp inside 56dp. Not a risk, and now
covered anyway.

It does **not** detect clipping by `ClipRect`/`ClipRRect`, by `Stack`
positioning, or horizontal truncation. Those are different shapes and this does
not pretend to cover them.

Boxes containing no text are skipped, which is what keeps it quiet: the
hundreds of `SizedBox(height: 8)` spacers hold nothing and never report.

## U-05 · Submitting a permit created no application — FIXED

M-42 was recorded as a cosmetic defect: fourteen confirmation screens showed
"View Application" and "Return to Applications" side by side, and both went to
`/app/applications`. Two buttons, one behaviour.

The reason there was no id to route to turned out to be the finding.

**The sixteen permit wizards were not creating an application at all.** Each
`_handleSubmit` called its own wizard provider's `submitApplication()`, which
sets that draft's status to `submitted` and notifies its own listeners, then
generated a reference number locally and navigated to the confirmation screen.
`ApplicationsProvider` — the only thing `ApplicationListScreen` reads — was
never touched.

What that meant for an applicant: complete nine steps, press Submit, read a
reference number, then open Applications and find it exactly as empty as
before. And no notification, because the submitted notification is posted by
`ApplicationsProvider.submitApplication`, which nothing reached.

### The fix

`lib/features/applications/presentation/widgets/submit_permit_application.dart`
records the submission, and all sixteen wizards call it. The confirmation
screens take the created application's id and "View Application" opens it.

Three decisions worth stating, because they are assumptions rather than
deductions:

- **The reference number is preserved, not replaced.** The repository would
  have minted its own `E-BPCO-2026-000007`, which would have meant the number
  on the confirmation screen and the number in the list were different numbers.
  The wizard's is passed through and stored instead. On a live build the
  server assigns one and the parsed response wins.
- **`businessName` carries the applicant's name.** A construction permit is
  filed by a person or a firm, not a business, and that field is what the
  detail screen labels "Business". The enterprise name wins when the applicant
  gave one. The backend should confirm the real shape.
- **`ApplicationType` is always `newPermit`.** The enum only offers
  new/renewal/amendment, which says nothing useful about a construction permit;
  `permitTypeLabel` is what actually names it on screen, and was added to the
  submit path for that.

The Building Permit wizard is wired too, though its confirmation screen has a
single action and never links to the application. It does not need the id — but
the record still has to exist, or the applicant's Building Permit is missing
from their own list.

Fifteen wizard test harnesses needed `ApplicationsProvider`, and their submit
taps needed a `pump(Duration(seconds: 1))`: the mock repository's delay is a
`Future.delayed`, which `pumpAndSettle` does not drain. That is the third time
that particular trap has cost time in this codebase.

## U-06 · The submission loop, verified end to end — DONE

U-05 tested the pieces: the record is created, the confirmation screen routes
to it. It did not test the path an applicant actually walks, and the pieces
were never what was broken — every wizard submitted happily, every confirmation

So `fencing_permit_wizard_test` now drives all nine steps, submits, and then

- the reference on screen names a real application in `ApplicationsProvider`
- an `applicationSubmitted` notification was posted
- pressing **Return to Applications** lands on the real
  `ApplicationListScreen` with that permit in it

The test's router registers the actual destination screens rather than stubs,
which is what makes the last assertion mean anything.

Confirmed non-vacuous the same way as U-01: with the wiring removed from the
fencing wizard, it fails with `Expected: contains 'FNC-2026-578196' / Actual:

One wizard is covered this way. Driving all sixteen through nine steps each

`test/architecture/wizard_records_submission_test.dart` asserts the cheap half
for the other fifteen: that the call is there at all. It reports nothing now
and would have reported all sixteen before U-05.

## U-07 · What happens when a repository fails — FIXED

Every pass so far has exercised the happy path. This one asked what the app
does when a fetch throws, which on the mock build never happens —
`MockBusinessRepository` and its siblings always succeed — and on the live
build is routine.

**Four of the five providers were written as though failure were impossible.**
`ApplicationsProvider` was the exception: it already had `loadError`,
`hasLoadError`, `isServingStaleData`, and a `finally` that clears the loading
flag whatever happens.

The other four did this:

```dart
Future<void> _load() async {
  _businesses = await _repository.fetchAll();   // throws here
  _isLoading = false;                            // never runs
  notifyListeners();                             // never runs
}
```

Measured rather than reasoned about. With a throwing repository:

```
>>> business isLoading=true count=0
>>> notifications isLoading=true count=0
```

`isLoading` stays true for the rest of the session — **the spinner never comes
down** — and the exception escapes to the zone unhandled on top of it.

`AuthProvider.login` had the same shape, on the screen where it costs most: a
transport failure skipped every `_isLoading = false` below it, so the Log In
button spun forever and the applicant was told nothing.

Fixed on the shape `ApplicationsProvider` already had — try/catch/`finally`,
with the error kept rather than swallowed, and whatever was already loaded left
alone. Sign-in and registration now distinguish "we could not ask" from "the
answer was no", which matters: *"Incorrect email or password"* after a dropped
connection sends someone to reset a password that was fine.

### Fixing that exposed the second half

Clearing `isLoading` on failure means the screens stop spinning — and fall
straight through to their empty state. Every list screen branched
`isLoading ? spinner : isEmpty ? empty : list`, with no branch for failure.

So the fix, on its own, turned a hung spinner into **"You have no applications
yet"** — a confident and false claim about the applicant's own filings. That is
arguably worse than the hang: a spinner is ambiguous, and this is wrong.

`lib/shared/widgets/states/load_failure_state.dart` gives failure its own
state, with a Try Again that calls the provider's `refresh()`.
`BusinessProvider` gained the `refresh()` the other three already had. Wired
into Applications, Notifications, Businesses and My Documents — the four
screens that render a loaded list.

`test/features/load_failure_states_test.dart` drives each of those screens with
a throwing repository and asserts they report the failure rather than claim
emptiness, and that no spinner is left up. It also asserts the genuine empty
state still appears when a load succeeds with no rows, so the new branch has
not simply swallowed the old one.

### Not a defect

Nine screens render lists with no empty handling at all — the Citizen's
Charter, Help & Support, notification preferences, the privacy policy, the
terms, the permit catalog. Every one is a fixed list defined in code. They
cannot be empty, and an empty state for them would be dead code.

## U-08 · The rest of the clipping blind spot — NO NEW DEFECTS

U-04 checked one shape: text taller than a box that pins its height. It said
plainly what it did not cover — `ClipRect`/`ClipRRect` and `Stack` — and those
are the shapes where a badge positioned near an edge, or a rounded card, cuts
a label off just as silently.

`test/support/clipping.dart` now covers both, and the axis rule differs by
shape. A fixed-height box is checked on **height only**, because one holding a
horizontally scrolling list is correct and its content is meant to run off the
sides. A clip is checked on **both axes**, because it cuts sideways too. A
`Stack` counts only when its `clipBehavior` actually clips — which is the
default, and easy to forget.

**No new defects.** 164 clip-and-stack pairs examined across the screens,
wizards and shell, alongside the 316 fixed-height pairs, and every one fits.

### The false-positive storm, and what it taught

The first run produced hundreds of findings — every off-screen label on every
scrolling screen, "extends 1734.0dp below the bottom of its ClipRect".

The check already skipped a clip with a `Scrollable` between it and the text.
That was the wrong direction. Dumping the ancestors of one offender showed why:

```
ClipRect rect=168..1200 ancestors=AnimatedBuilder < NotificationListener<ScrollNotification>
  < StretchingOverscrollIndicator < Scrollable < PrimaryScrollController < ListView
```

The clip is *inside* the `Scrollable`, not outside it — `StretchingOverscrollIndicator`,
the Android overscroll effect Flutter inserts into every scroll view, is built
from a `ClipRect` around the whole viewport. It is the clip that makes
scrolling work, so everything below the fold sits outside it, correctly.

Excluding the overscroll indicator specifically, rather than "anything inside a
`Scrollable`", is what keeps the check worth having: nearly all of this app's
content is inside a scroll view, and an author-written `ClipRRect` in a list is
exactly the kind of thing worth catching.

Validated against deliberately broken cases before being trusted — text wider
than a `ClipRect`, and a `Positioned` label past a `Stack`'s edge — and both
report. Then confirmed non-vacuous, since a check that finds nothing because it
examines nothing is worse than no check at all.

## U-09 · The Drafts tab was structurally empty — FIXED

The same disconnect as U-05, one layer over, and it was worth confirming rather
than assuming.

`ApplicationSegment.drafts` filters `ApplicationsProvider` for
`applicantStatus == ApplicationStatus.draft`. **Nothing in this app ever
creates an application with that status.** Every occurrence of
`ApplicationStatus.draft` in `lib/` is a `switch` case handling it or the
lifecycle projection mapping to it; none constructs one. Drafts live in the
sixteen wizard providers, where `saveAsDraft()` sets the *wizard's* draft
status and touches nothing else.

Measured, with a saved fencing draft in the tree:

```
>>> fencing provider has a resumable draft: true, summary: true
>>> segment chip says: Drafts (0)
```

So the tab named Drafts could never show one, however many half-finished
applications the applicant had.

What makes this worse than an empty tab: the app already *knows*.
`DraftRegistry.summaries` gives permit label, last-saved date, progress and a
resume route, and `MainShell` reads it on its first frame to nudge the
applicant about drafts left idle for a week. **The app was notifying people
about work it gave them nowhere to see.**

### The fix

The Drafts segment now reads `DraftRegistry.summaries(context)` — the source
that actually holds drafts — with its own tile showing progress, when it was
last saved, and a tap that resumes the wizard at its route. The chip counts the
same source. Search filters drafts by permit name.

`_DraftTile` is deliberately not `ApplicationListTile`: a draft has no
reference number, no status and no service pledge, which is most of what that
tile exists to show.

### Two consequences worth recording

**`ApplicationListScreen` now needs all sixteen wizard providers**, because the
registry looks them up by type. That is the same coupling `MainShell` already
had. Rather than spell sixteen lines out in each affected harness,
`test/support/wizard_providers.dart` supplies them, and `main_shell_test`
collapsed onto it too.

**Two draft labels were wrong once they became visible.** These strings only
ever appeared inside notification prose before; the Drafts segment puts them on
screen as titles, next to each other. Fifteen were bare permit names —
"Fencing", "Demolition", "Civil / Structural" — while Sign said "Sign Permit"
and Interior Design said just "Interior". Corrected to match.

## U-10 · Writes that fail — FIXED

U-07 covered the reads. A failing read shows the wrong thing; a failing write
loses work, and every write in the app was unguarded:
`submitApplication`, `attachPayment`, `advanceStatus`, `registerBusiness`,
`rename`, `remove`. Only `_finalizeImport` had a `try`.

### The submission, which I had just built

The worst of them was new. U-05 gave the wizards an `await` that can throw, and
nothing caught it — so the throw skipped the `pushReplacement` at every one of
the sixteen call sites. **Pressing Submit after nine steps did nothing at all**:
no confirmation, no error, no way to tell whether the application had been
filed. Confirmed rather than assumed:

```
>>> submit threw: true -> Exception: offline
```

`submitPermitApplication` now returns null on failure, having told the
applicant, and every wizard checks for it. Failure is handled in the one shared
place for the usual reason, and the draft is deliberately left intact — the
applicant is still on the last step with everything they entered and can press
Submit again.

The Building Permit wizard needed the check even though it ignores the id:
without it a failed submission would have shown a confirmation screen for an
application that was never filed.

### Registering a business

Same shape as the sign-in defect: `_isSubmitting` set true before the await, so
a throw left the button spinning for good — no message, no way back, and a
filled-in form that could not be resubmitted. Guarded, with the error said out
loud and the button released.

### Not fixed, because nothing calls it

`ApplicationsProvider.attachPayment` and `advanceStatus` are unguarded too, and
neither is reached from anywhere in `lib/features`. They are dormant in the
same way T-01's four subsystems are. Guarding a path nothing walks would
have looked like progress without being any.

Both tests were checked against the unguarded code before being kept. The
registration one falsifies cleanly — no message appears. The submission one
can only be falsified by reverting its return type as well, since nullability
is part of the fix, so it fails to compile rather than failing behaviourally;
the probe above is the behavioural evidence.

## U-11 · Every route entered cold — NO DEFECTS, after two false starts

A route is normally reached by tapping through the app, which hands it `extra`.
It can also be reached with none of that: from a notification, a restored
session, a deep link, or the router rebuilding after a hot restart. Nothing had
ever checked what happens then, and the fifteen confirmation screens each read
four or five values out of `extra`.

`test/routes/cold_entry_test.dart` drives all 49 reachable routes with no
`extra`, giving path parameters ids that do not exist — the realistic failure,
being a notification about an application the server has since dropped.

**Nothing threw.** The router's `extra` reads all carry fallbacks, and the
screens tolerate a missing record. A clean result.

### It took two false starts to earn that result

The first version **built a second router** and called `go` on it, while the
mounted app used a different instance. It navigated nothing.

The second version fixed that and still passed all fifty — which was the
warning. With a fresh `AuthProvider`, `AuthStatus` is `unknown`, and
`_redirect` sends *every* location to `/splash`. Fifty tests rendered the
splash screen and asserted that it did not throw.

The fix is two assertions, not one: sign in first, then assert the router
**landed on the path asked for**. Falsified by removing the sign-in, which
turns all 44 green cases red with `Expected: '/business' / Actual: '/login'`.

### And the auth routes belong to a different session state

Six routes then failed — `/login`, `/register`, `/forgot-password`,
`/registration-success`, `/splash`, `/onboarding`. Not defects: a signed-in
applicant is *deliberately* bounced off the sign-in screens to `/app/home`.
The sweep now splits by the session state each route actually belongs to, and
asserts the redirect contract in both directions rather than deleting the
inconvenient cases.

### The lesson, which is not new

This is the third time in this sweep that a test passed for the wrong reason —
after the accessibility groups that examined no boxes, and the clipping check
that reported every off-screen label. **A green sweep is a claim, and the claim
has to be falsified before it is believed.** Every check added since has been
checked against deliberately broken code first.

## TAB 00 · Shared vocabulary &amp; parity guard — DONE, and it caught five

The first TAB of the admin-parity programme. `lib/core/contract/admin_vocabulary.dart`
carries the admin's vocabularies byte for byte, generated from
`Upupapp/eBPCO-Web @ e3cd7c3` rather than retyped — the permit catalog contains
an EN DASH (U+2013) that hand-copying gets wrong once and then nobody can find.

Eight vocabularies mobile did not have are declared: the 19 permit types,
document status (8), assessment status (8), payment transaction status (4),
collecting agency, payment adjustment type, and contact verification status and
method. Each has a `wire` value and a `fromWire` that **throws on an unknown
value rather than defaulting**, mirroring the admin's own `isValidPermitType`.
A silent fallback turns a contract break into a wrong screen.

Six vocabularies mobile already had are **asserted, not duplicated** — the
19-state lifecycle, evaluation stage and result, payment method, release method
and release status. Adding a second enum beside an existing one is the failure
this file exists to prevent, and committing one while preventing it would have
been absurd. All six match the admin exactly.

### What it found immediately

Five of the sixteen wizards were filing a permit type the admin would reject,
and **four of those were introduced by U-05** — when the wizards were first
wired to record submissions, each was given a hand-written label:

| Filed | Admin expects |
|---|---|
| `Building Permit` | `Building Permit – New Construction` |
| `Building Permit — Addition / Extension` | `Building Permit – Addition / Extension` |
| `Building Permit — Renovation` | `Building Permit – Renovation / Alteration` |
| `Excavation & Ground Preparation Permit` | `Excavation Permit` |
| `Sanitary / Plumbing Permit` | `Sanitary Permit` |

Two of them differ only by an em dash where the admin uses an en dash. None of
it fails anything: the application files, the confirmation screen renders, and
the value is only wrong when it reaches a portal that validates it — by which
time it is an applicant's filing.

All sixteen wizards and all fifteen confirmation screens now use
`CanonicalPermitType.<type>.wire`, and
`test/architecture/canonical_permit_type_test.dart` fails on a literal. It
would have fired on `'Building Permit'` at the previous commit.

### The lesson

This is the cost of choosing strings by hand, priced. U-05 was careful work
that shipped with tests, and it still put four wrong permit names into the
filing path, because nothing existed to compare them against. **The guard found
in one run what four days of green suites had not.**

## TAB 02 · Per-document review status — DONE (G-01, G-02, G-18)

The highest-exposure gap in the parity register. The admin tracks each
submitted document through eight states — Missing, Uploaded, Submitted, Under
Review, Accepted, **Rejected**, **Revision Required**, Expired — and requires
the evaluator to write a reason whenever it lands on one of the last two.

Mobile's `DocumentModel` was `id · label · fileName · uploadedAt ·
fileSizeBytes · filePath`. **No status field at all.** A document turned back
for revision, with the evaluator's reason recorded against it in the portal,
showed on the applicant's phone as a document that had been sent. They found
out only if somebody separately raised a Letter of Instruction about it.

### The shape of the fix

The review fields went onto `DocumentModel` as **nullables**, rather than
introducing a separate type for filed documents. `ApplicationModel.documents`
is a `List<DocumentModel>`, and changing that type would have rippled through
the repositories, the DTO and every wizard's submit path for no gain the
applicant can see.

Null status means "not reviewed", which is honest rather than convenient: a
file the applicant has picked but not sent has no review status, and rendering
one would be a claim about a decision nobody has made. The detail screen says
"Not yet reviewed" for exactly that case.

Added: `status`, `remarks`, `issuingOffice`, `issueDate`, `expiryDate`, and a
`history` of earlier submissions.

### Three decisions worth recording

**`needsApplicantAction` excludes `underReview`.** Nothing has been handed back
yet; telling the applicant to act would be asking them to guess ahead of the
office. It covers rejected, revision-required and expired only.

**Expiry is computed, not waited for.** A clearance whose `expiryDate` has
passed reads as expired whether or not the desk has marked it. The applicant
can act sooner than the office will, and should — the alternative is learning
about a lapsed barangay clearance at the counter.

**Resubmission appends.** `resubmittedWith` keeps the previous filename, its
status and the reason it came back, and clears the remarks on the new
submission — the old rejection does not describe the new file. The office keeps
this history and never clears it; so does this.

### Display

Documents needing action sort first. A rejected document eleventh in submission
order is a document the applicant does not know about. The evaluator's remarks
render in full beneath the row, the issuing office is named where known, and
earlier submissions are acknowledged by count.

Seventeen tests: twelve on the model's decisions, five driving the detail
screen with a rejected document and asserting the applicant can actually read
the reason.

### The resubmit loop — closed 27 August

`ApplicationsRepository.resubmitDocument` now exists on the interface, the mock
and the HTTP repository; `ApplicationsProvider.resubmitDocument` returns null on
failure rather than throwing, and the detail screen offers **Replace this
document** on anything needing action.

The button appears only where the office has actually asked for something
different. A Replace action on an accepted document invites an applicant to undo
work that was already signed off.

Driven end to end in a test: tap Replace, supply a file, and the row moves from
Rejected to the new filename with the rejected version kept in history. Failure
tells the applicant and leaves the application untouched.

**The backend route does not exist yet.** `POST
/applications/:id/documents/:documentId/resubmit` is what the HTTP repository
posts to, and it is recorded here as a hand-off rather than faked — on a live
build this should fail loudly, not quietly tell an applicant their document was
resent.

## TAB 06 · Partial payment, rejection and balance — DONE (G-03, G-04)

The admin's own comment on its `PaymentStatus` vocabulary says it plainly:
mobile's four values *"have no room to represent"* genuine partial payment of a
staged or legally-prescribed charge, and every consumer of the type "must
handle it explicitly rather than falling through a default case".

Mobile also carried a single reference, method and proof per assessment. That
is enough for "the applicant paid" and not enough for **"the applicant paid
twice, and the first was rejected"** — which is what the portal records, and
what decides whether anything is still owed.

### What was added

`PaymentTransactionRecord` — one payment against an assessment, with its own
amount, method, reference, status, rejection reason and void flag. An
assessment now carries a list of them, and derives:

- `amountPaid` — **verified and unvoided only**
- `balanceDue` — the total less that
- `isPartiallyPaid`
- `rejectedTransactions` — what the applicant still has to deal with

`partiallyPaid` joined the status enum, which the compiler then made
unmissable: the exhaustive switch in the Order of Payment screen refused to
build until it was handled.

### The rule that decides the numbers

**Only a verified, unvoided payment counts toward the balance.** A rejected one
is money the office did not accept; counting it would tell the applicant they
owe less than they do. A voided one is kept for audit and excluded from every
total, exactly as the admin does — anything else would leave the two halves
disagreeing about what is owed, which is the worst possible thing for them to
disagree about.

Amounts stay in integer centavos throughout, asserted.

### Display

The fee breakdown gains **Paid** and **Balance due** rows, shown only once
something has actually been accepted — "Paid ₱0.00" on an untouched assessment
is noise dressed as information. Rejected payments get their own panel above
the status, with the office's reason in full and the plain statement that
*"This amount has not been credited to your assessment."*

Without the reason, an applicant knows only that a payment failed, and cannot
tell whether to resend the same proof, a different one, or a different amount.

Eleven tests on the arithmetic and the rules.

### Not built

The **Official Receipt** and the **collecting agency** (OBO/LGU versus BFP) are
TAB 07 and remain open. `PaymentTransactionRecord` deliberately does not carry
an OR number yet: inventing one in a mock is exactly the failure mode the admin
warns about in its own source, where the field is marked "never auto-filled".

## TAB 07 · Official Receipt and collecting agency — DONE (G-05, G-12, G-19)

An Official Receipt is the applicant's proof that a government office took
their money, and the number they will be asked to quote at a counter.

The app referenced an OR number in four wizard steps and one notification
payload while `PaymentAssessmentModel` had a single nullable field nothing
populated — so the number an applicant would actually be asked for lived
nowhere.

### Added

On each payment: `agency`, `orNumber`, `orDate`, `orIssuedBy`. On the
assessment: `receipts` (issued and unvoided only), `collectingAgencies`, and a
list of `PaymentAdjustmentRecord` — void, reversal, refund, correction.

The Order of Payment screen gained a receipts panel where the number is set in
the section-title face with a **copy button**: the applicant is asked to quote
it at a counter, so it has to leave the phone without being retyped. Beneath it
the amount, the receipt date and the collecting agency. Adjustments get their
own panel with type, amount and the office's reason, rather than being folded
silently into the balance — an applicant whose total changes without
explanation cannot tell a refund from an error.

### Two rules worth stating

**The BFP is not the LGU.** `CollectingAgency` distinguishes them because FSEC
and FSIC fees are collected by the Bureau of Fire Protection. An applicant sent
to the OBO cashier to settle a BFP fee has been sent to the wrong counter.
`collectingAgencies` excludes voided payments — a voided BFP payment does not
mean the BFP collected anything.

**An OR number is never fabricated.** The admin marks its field "never
auto-filled" and the same holds here: a plausible-looking receipt number
invented by a mock is *worse* than an empty field, because the applicant would
quote it. `official_receipt_test.dart` scans `lib/` and fails on any OR
assigned from a literal or from the clock — the trick the wizards legitimately
use for their own reference numbers, which must never be applied to a receipt.

That guard was checked against a realistic fabrication before being trusted. A
first attempt at falsifying it used a helper the pattern does not match and
passed, which proved nothing; stamping `orNumber = 'OR-2026-000123'` into the
mock repository made it fail as it should.

## Auditing the guards themselves — ONE WAS BLIND

Ten guards had been written across this sweep, each claiming to prevent a
defect that had already happened at least once. None had been seen to fail
since the day it was written.

Two things this session made that worth checking. U-01 shipped a scanner that
inspected only *named* async methods and missed **127** anonymous closures with
the same defect, while reporting the job done. And the Official Receipt guard
passed a falsification that had not actually violated its rule — proving
nothing, and looking like proof.

`tool/guard_audit.py` breaks each guard's rule in `lib/`, runs the one test that
should catch it, and restores the file. It is a script and not a `_test.dart`
on purpose: it mutates the source tree and must never run inside
`flutter test`.

### Result: 9 of 10, and the tenth was blind

**`status_badge_usage_test` passed with a hand-rolled pill sitting in the
tree.** Its rule skipped any `Row` that already contained a `StatusBadge` — so
a pill built by hand *beside* an existing badge was exempt, which is precisely
how that defect would reappear. Nobody adds a hand-rolled pill to an empty row;
they add one next to the badge that is already there.

The exemption was never needed. Code that uses `StatusBadge` does not write
`borderRadiusPill`, because the widget owns its own radius — so the constant
appearing in a Row body already means someone built the pill by hand. Removing
the exemption closed the hole and left the suite green.

Re-run after the fix: **10 of 10**.

### The first attempt at this audit also failed, quietly

The status-badge mutation did not apply — the anchor string was wrong — and the
harness reported MISSED for a guard it had never actually challenged. That is
the same failure shape as the Official Receipt falsification an hour earlier:
**a test that did not run reads exactly like a test that passed.** The harness
now distinguishes "mutation failed to apply" from "guard did not catch it", and
says which.

## TAB 12 · Citizen's Charter across all 19 permit types — DONE (G-17)

RA 11032 requires the LGU to publish, for every service, what it costs, how
long it takes and what the applicant must bring. Surfacing it is what lets an
applicant hold the office to a stated standard instead of guessing.

### The real defect was worse than the recorded one

G-17 said the charter covered five permit types of nineteen. It was not that
simple, and the truth was worse.

The charter was **keyed on the app's own short display names** — `'New
Construction'`, `'Fencing'`, `'Interior'` — while the requirements catalog and
the admin portal both key on the office's name: `'Building Permit – New
Construction'`. `charterFor` falls back to a generic ancillary entry for
anything it does not recognise, so the mismatch never failed; it silently
answered with the generic entry.

**And it had already broken TAB 01.** The pre-flight screen looks the catalog
up by the permit type it is handed, and the catalog screen navigates with
`option.title` — the short name. So `requirementsForLabel` returned null in the
running app and the catalog facts added in TAB 01 — official form, required
count, validity — **never appeared at all**. The TAB 01 suite passed because it
was fed canonical strings the app never produced.

That is the third time this sweep that a test passed on data the app does not
generate.

### The fix

`_PermitOption` gained a `canonical` type and a `lookupKey`, so navigation
carries the office's name rather than the card's label. The charter map is
re-keyed to the same strings. One vocabulary end to end, which is what TAB 00
existed to establish and what this closes the last gap in.

Three entries were added rather than left to the generic fallback, because for
these the fallback was **wrong, not merely vague**: it named the Office of the
Building Official for all of them. Zoning belongs to the MPDO; both fire
clearances belong to the BFP, which also collects their fees.

`charter_coverage_test.dart` asserts an entry for all nineteen, membership
rather than fallback for the eight described ones, and that the three
non-OBO offices agree with the requirements catalog's `responsibleDepartmentId`.

### Two smaller things

The existing "no entry quotes a fee amount" rule flagged `RA 9514` — a statute
number is not a peso figure. The rule now strips statute citations before
looking for a figure, and was checked to still catch `PHP 1500`.

An assertion I wrote compared requirement *counts* to prove an entry was not
the generic fallback. One entry legitimately has the same count, so the test
reported a fallback that had not happened. It now asserts map membership, which
is what it meant.

### A mistake worth recording

Restoring an injected test fixture with `git checkout -- <file>` **discarded
the whole uncommitted TAB 12 charter edit**, not just the injection. The work
was redone from the transcript. Use a copied backup for mutate-and-restore, not
a git restore, on a file with uncommitted work.

## TAB 08 · Assessment versions — DONE (G-13, G-14)

The office does not edit an issued assessment. A correction after issuance
builds a **new version** and marks the old one superseded, so the figures an
applicant was shown before are still the figures they were shown — which
matters if they paid against them.

Mobile had a single Order of Payment with no version and no status. A
reassessment looked exactly like the original: a total that had silently
changed since the applicant last looked, which reads as a bug in the app rather
than a decision by the office.

### Added

`OrderOfPayment` gained `version`, `status` (the admin's eight-value
`AssessmentStatus`) and `revisionReason`, plus `isPayable`. The assessment
keeps `supersededOrders` — every version it replaced, newest first — and
`wasReassessed`.

### The rule that changes behaviour

**`amountDue` is null when the current order is not payable.** A superseded,
voided or draft assessment has no figure the applicant should act on, and
returning its total would invite payment against an amount the office has
replaced. This is the one case in the app where a blank is better than a
number.

Payments already made survive a reassessment — asserted. The applicant paid
against version 1; that money does not vanish because the office reassessed, so
`amountPaid` still counts it and the balance is computed against the new total.

### Display

A panel above the receipts states that the assessment was reassessed, names the
version to pay against, gives the office's reason, and lists each superseded
version with its date and its total. "The figure changed" with no way to see
what it was before is not an explanation.

Twelve tests: nine on the model's rules, three driving the screen — the
distinction that has mattered repeatedly here, where a suite has passed on
values the running app never produced.

## TAB 03 · Zoning / Locational Clearance — DONE (G-06)

The first of the three permit types the admin portal recognises and this app
could not file. It matters more than one permit's worth, because **most other
permit types list a Locational Clearance among the documents an applicant must
already hold** — so the app was asking for a clearance it gave no way to
obtain.

Built from the Municipality of Castilla MPDO's own **Form FM-MPD-12**, as
transcribed in the requirements catalog: five steps, sixteen documents,
thirteen of them required, twelve-month validity.

### Two things it does differently, on purpose

**It is not the OBO's.** Locational clearance is issued by the Municipal
Planning and Development Office and assessed under the zoning ordinance rather
than the National Building Code. The wizard header, the confirmation screen and
the Citizen's Charter entry all say MPDO.

**It states the ocular inspection.** FM-MPD-12's own procedure is a site
inspection and an evaluation report by the Zoning Officer, so the certification
step asks the applicant to acknowledge that someone will visit the lot. An
applicant who does not expect that is an applicant who is not there when it
happens.

The three conditional documents — owner's written consent, DPWH clearance, ECC
— say what the condition is rather than appearing as flat requirements.

### The census caught a real defect immediately

Every one of the app's 141 existing wizard steps passes
`centerVertically: false` to `FormScrollScaffold`. My five new ones did not, and
the default is `true` — which reads `constraints.maxHeight` and produces
`minHeight: Infinity` inside an unbounded parent. The upload-slot census, which
mounts each step on its own, failed with *"BoxConstraints forces an infinite
height"* the moment the new step was added to it.

That is the census earning its place two days after being written: a
copy-shaped mistake in new code, caught by a harness built to measure something
else entirely.

### Coverage

The wizard is driven end to end — all five steps, every required document, to a
filed application. It is registered in `DraftRegistry` (whose staleness guard
correctly failed until it was), the shared wizard-provider helper, the
upload-slot census at sixteen slots, and the terminal-screen accessibility
suite.

## TABs 04 & 05 · FSEC and FSIC — DONE (G-07, G-08)

The last two permit types the admin portal recognises and this app could not
file. Built together because they share a shape: both are BFP clearances, both
preconditions under RA 9514, both from real BFP Castilla Fire Station forms —
**BFP-QSF-FSED-001** and **-002**.

- **FSEC** gates the Building Permit. The app's Fire Safety evaluation stage
  had been reporting on a clearance the applicant could not apply for.
- **FSIC** gates the Certificate of Occupancy — whose wizard has an upload slot
  for an FSIC to this day, and until now gave no way to obtain one.

Four steps each: applicant, project, documents (9 and 10 respectively, from the
catalog), certification.

### The thing both wizards keep saying

**The Bureau of Fire Protection is not the LGU.** It issues these, it inspects
against them, and it collects their fees. Every screen an applicant might read
as a bill says so, because sending someone to the OBO cashier to settle a BFP
fee sends them to the wrong counter — the same distinction TAB 07 put into
`CollectingAgency` and TAB 12 into the charter.

The FSIC's awkward document is called out by name in its test: an **endorsement
from the Office of the Building Official**. The applicant has to get the
building office to endorse before the fire office will inspect, and a
requirements list that buries that is a list that costs someone a week.

### With this, the catalog is complete

All **19** permit types the admin recognises can now be filed from the app.
`DraftRegistry` names nineteen providers, and its staleness guard was updated
from sixteen — having correctly failed twice on the way.

### A mistake, caught fast

Wiring these I ran `dart format lib/`, which reformatted **80 files** including
the Android lane's. Caught it on the next command, restored the 76 unintended
ones from `HEAD`, and kept only the four I meant to change. This is the second
time in this sweep that a tree-wide format has done that; the rule stands and I
broke it. Format single files.
