Each TAB is one self-contained command. A TAB carries the imperative, the reason it exists, a scope table, a concrete technical specification, the standards it is held to, and acceptance criteria that can be checked without asking anybody's opinion. TABs are executed in order within a phase; phases overlap only where the dependency map in section D says they may.

A TAB is complete when its acceptance criteria pass on evidence — a test run, a scan report, a signed decision — not when the work feels done. That distinction is not pedantry: the previous programme recorded five TABs as complete on section-level acceptance while rows of their own scope tables had never been built, and the gap was only found by auditing the tables directly.

1   The Master Command

Build and operate one authoritative eBPCO service, and integrate the applicant mobile app and the LGU web admin against it, so that a building permit application submitted on a phone and the officer's decision on it are the same record — to a standard that survives an audit, a penetration test, and the Data Privacy Act.

1.1   Non-negotiables

RuleWhy it is not open for discussion
The server is the recordLifecycle status, classification, assessed amounts, evaluations, and release records are decided by the backend and never by a client. Two clients each computing their own view of a permit's state is how an applicant and an officer end up disagreeing about whether a permit was issued.
One contract, machine-readableThe OpenAPI document is the single source of truth. Mobile DTOs, admin TypeScript models, and server handlers are all generated from or validated against it. A contract that lives in three hand-written copies has already drifted.
Money is integer centavos, end to endAlready true in mobile (PesoAmount) and admin (assessedAmountCentavos). The wire format and the database must match. A float anywhere in a fee path is a defect, not a rounding preference.
No invented figures, everNo Order of Payment means no amount is shown and no payment can be started. An estimate on a government fee screen is a misrepresentation.
Unknown enum values are rejected, not defaultedMobile's DTO layer already throws on an unrecognised status. Keep it. Silently mapping an unknown server state to a plausible client state is how an applicant is told a rejected permit is under review.
Never assert a pledge the LGU has not madeRA 11032 countdowns must derive from the LGU's published Citizen's Charter. Where charter data is missing, the app says "approximate" or "awaiting classification". Guessing risks falsely accusing the LGU of lateness.
Personal data is minimised and accounted forEvery field collected must map to a lawful basis and a retention period under RA 10173. "We might need it later" is not a basis.
No production action without a runbookDeploys, migrations, and rollbacks are written down and rehearsed before they are performed on real applicant data.

1.2   Technical constitution

  • Trunk-based development with short-lived branches; every merge to main is releasable.
  • Conventional Commits and Semantic Versioning across all three repositories.
  • Everything as code — infrastructure, pipelines, database schema, alerts, dashboards.
  • No shared mutable state between services without a migration path. The in-memory admin store is the thing being removed; do not recreate it server-side as a singleton.
  • Tests are the specification. A behaviour without a test is a behaviour nobody has agreed to.
  • One clock per feature. Time is injected, never read from the wall clock inside presentation code — see the 19 August 2026 fix in TAB 18.

TAB 01Ratify the API contract
Priority P0  ·  Owner Backend Mobile Admin  ·  Depends on nothing  ·  Blocks every other TAB
Command
Produce a single, versioned, machine-readable OpenAPI 3.1 description of the eBPCO API, reconciled against the admin's domain vocabulary and the mobile client's existing DTO layer, reviewed and formally accepted by the LGU and both client owners. Generate client and server types from it. Retire every hand-maintained copy of the contract.

Why this is TAB 01

Mobile already ships a client for five endpoints and a JSON shape it invented. Admin already ships a 19-value lifecycle vocabulary, a payment model in centavos, and document and evaluation models. These two were written to describe the same permits and have never been compared field by field. Building a server against either one, or against a third reading, guarantees an integration failure discovered late — and the loudest failures will be enum mismatches, which mobile is designed to reject loudly rather than absorb.

Scope

Vocabulary reconciliationA field-by-field table mapping admin's ApplicationRecord, PaymentTransaction, ApplicationDocument, EvaluationRecord, GeneratedPermit, PermitReleaseRecord and AuditEvent onto mobile's models and onto the canonical wire shape. Every divergence resolved in writing.
Lifecycle projection, formalisedThe 19 admin states → 7 applicant-visible states mapping moves out of a TypeScript comment (LIFECYCLE_TO_MOBILE_LABEL) and into the contract as a normative table, so both clients project identically.
Endpoint setConfirm, correct, or replace the five endpoints mobile assumes, and add the ones no client has yet needed. Minimum surface in the specification below.

Contract rules that must be normative, not advisory

  • Money. Every monetary field is an integer of centavos, named with a Centavos suffix. Floats are rejected by schema, not coerced.
  • Enums. Closed enumerations carrying the admin's exact string labels. Clients reject unknown values; the contract therefore treats adding an enum value as a breaking change requiring a version bump.
  • Timestamps. RFC 3339 with explicit offset. The server stores UTC; the Philippines has no DST but the app must not assume a fixed offset in perpetuity.
  • Errors. RFC 9457 Problem Details for HTTP APIs for every non-2xx, with a stable machine-readable type. Mobile's ApiException maps onto it.
  • Idempotency. Every non-GET that creates or moves money or state accepts an Idempotency-Key and returns the original result on replay. A resubmitted permit application after a dropped connection must not become two applications.
  • Pagination. Cursor-based, stable under insertion. Offset pagination silently skips records when an officer files something mid-scroll.
  • Concurrency. ETag / If-Match on mutable resources, so two officers editing one evaluation produce a 412 rather than a silent overwrite.

Acceptance criteria

  • The OpenAPI document validates against the 3.1 specification in CI, on every commit.
  • Every field in admin's seven domain models appears in the contract or is explicitly recorded as client-local with a reason.
  • Every endpoint mobile's ApiClient calls exists in the contract with a matching shape, or mobile has been changed to match.
  • The 19→7 lifecycle projection is expressed in the contract, and a generated test asserts both clients implement it identically.
  • Mobile Dart DTOs and admin TypeScript models are generated artefacts; a CI job fails if a hand edit diverges from generation output.
  • A published example payload exists for every endpoint and is used as a fixture by all three tiers.
  • Written acceptance recorded from the LGU technical representative and both client owners, closing M-21.
Do not skip the reconciliation table. It is tempting to declare mobile's assumed shape "the contract" because it is already written and already tested. It was authored without the admin in the room, and the admin is the system of record for everything it describes. Reconcile, then ratify.

TAB 03Identity, authentication, and session
Priority P0  ·  Owner Backend  ·  Depends on TABs 01, 02  ·  Blocks TABs 05–13  ·  Closes M-01, M-22
Command
Implement server-side identity for two distinct populations — applicants and LGU staff — with OAuth 2.0 / OIDC token issuance, rotating refresh tokens, revocation, role and permission enforcement, and account recovery, meeting NIST SP 800-63B. Every API route except the explicitly public ones must be deniable by default.

Why

Mobile currently authenticates against a local PBKDF2 verifier and sends no Authorization header because LocalStorageService.sessionToken() returns null. Admin has a session service and route guards with no server behind them. Both are honest placeholders for a thing that does not exist. Until it does, there is no identity, no authorisation, and no way to answer "who changed this permit".

Scope

AreaRequirement
Two populations, one mechanismApplicants self-register and can only ever see their own records. LGU staff are provisioned by an administrator and carry roles. Both authenticate through the same token endpoint with different scopes — one mechanism, so there is one place to get it right.
Credential storageArgon2id (memory-hard, tuned to the deployment) or PBKDF2-HMAC-SHA256 at a current iteration count, unique salt per credential, pepper in the secret manager. Never reversible, never logged, never returned.
Password policyPer NIST SP 800-63B: minimum length over composition rules, screening against known-breached password lists, no forced periodic rotation, no knowledge-based questions.
TokensShort-lived access token (≤15 min) carrying subject, scopes and roles. Refresh token, long-lived, rotating with reuse detection — a replayed refresh token invalidates the whole family and raises a security event.
RevocationSign out, sign out everywhere, and administrative revocation, all effective within one access-token lifetime.
AuthorisationDeny by default. Object-level checks on every record access — OWASP API Security's top risk is exactly an applicant reading another applicant's permit by changing an ID. Enforce in the domain layer so no new controller can forget.
Brute-force and enumeration defenceRate limiting and progressive delay per account and per source. Registration, login and password-reset responses must not reveal whether an account exists.
Account recoverySingle-use, short-expiry, side-channel-delivered reset tokens. Completing a reset revokes all existing sessions.
MFA for staffTOTP at minimum for any role that can approve, assess, or release a permit. Optional for applicants; mandatory for staff.
Identity proofingDecision E-5: how an applicant is proven to be who they claim. Options range from email verification to PhilSys. Affects legal weight of a filing under RA 8792.

Acceptance criteria

  • Every route is denied without a valid token except a documented public allow-list, proven by an automated test that enumerates routes from the contract.
  • An applicant requesting another applicant's application by ID receives 404 — not 403, which confirms existence — and the attempt is recorded as a security event.
  • A staff member without the required permission receives 403 and no partial data.
  • Replaying a rotated refresh token invalidates the family and raises an alert; a test asserts it.
  • Password reset invalidates all sessions; a test asserts an old access token stops working within its stated lifetime.
  • No credential material appears in any log at any level; asserted by a log-scanning test.
  • Timing and response bodies for login and registration are indistinguishable between existing and non-existing accounts.
  • Staff MFA cannot be disabled by the staff member alone.
TAB 04Canonical data model and persistence
Priority P0  ·  Owner Backend  ·  Depends on TABs 01, 02  ·  Blocks TABs 05–09
Command
Design and migrate the authoritative relational schema for applicants, businesses, applications, documents, evaluations, assessments, payments, permits, releases, notifications and audit events — with referential integrity, constraints that make the non-negotiables unrepresentable, versioned migrations, and a retention model that satisfies RA 10173 by construction rather than by policy document.

Design rules

  • Make illegal states unrepresentable. If a payment cannot exist without an Order of Payment, that is a foreign key and a NOT NULL, not a code comment. If money is centavos, the column is BIGINT and there is a CHECK constraint that it is non-negative.
  • The lifecycle is data, and its transitions are constrained. Status is an enumerated column; a transition table records which moves are legal. An officer cannot jump an application from Submitted to Released because a UI bug allowed it.
  • Every mutation is attributable. created_by, updated_by, created_at, updated_at on every table, non-null, set by the persistence layer rather than by callers.
  • Soft-delete only where the law requires retention; hard-delete where the law requires erasure. Decide per table, in writing, and enforce it in the schema.
  • No natural keys as primary keys. Permit numbers change format; UUIDs do not.
  • Personal data is inventoried at the column level, tagged in the schema, so TAB 20's records of processing can be generated rather than hand-compiled.

Scope

DeliverableDetail
Schema and ERDDerived from the ratified contract, not invented alongside it. Published as part of the contract repository.
Migration frameworkVersioned, forward-only, reviewed, each migration reversible or explicitly documented as not. Applied automatically in the pipeline; never by hand in production.
Seed and fixture dataReference data (permit types, charter classifications, holidays) seeded reproducibly. Synthetic applicants for staging — never a copy of production.
EncryptionEncryption at rest for the database and object store. Field-level encryption for identity documents and any government-issued identifier, with keys in a managed key service and a documented rotation procedure.
Backup and recoveryAutomated backups, encrypted, retention per policy, and — the part usually skipped — a rehearsed restore with a measured recovery time.
Indexing and constraintsIndexes for every query the contract implies. Unique constraints on anything the domain says is unique, including permit numbers.

TAB 07Assessment and payments

TAB 18Test strategy and CI/CD
Priority P1  ·  Owner Backend Mobile Admin  ·  Start during Phase A  ·  Closes G8
Command
Establish continuous integration for all three repositories, add consumer-driven contract testing between the tiers, build an end-to-end suite over the critical journeys, and enforce the quality gates that make "it passed" mean something.
There is no CI in any repository today. The mobile app's 443 tests and clean analyzer are real and valuable, but they are run by hand. That is why a time-dependent test could sit broken until someone happened to run the suite — and why nothing catches an admin change that breaks the contract. CI is the mechanism that turns a good test suite into a guarantee.

Test strategy

LayerCoverage
UnitDomain logic, state machines, money arithmetic, the pledge clock. Fast, deterministic, no I/O. Property-based tests for arithmetic and date computation, where example-based tests systematically miss edge cases.
ContractConsumer-driven contracts (Pact or equivalent) between each client and the API. Provider verification runs in the backend pipeline, so a breaking server change fails before it reaches a client — the single highest-value test type in a three-tier system with two independent client teams.
IntegrationBackend against a real database and object store in containers. No mocked persistence: the constraints in TAB 04 are part of the behaviour under test.
Widget / componentMobile widget tests (extend the existing 443) and Angular component tests. Forms tested at a 400dp viewport — a wider window hides real overflows, which is how a missing isExpanded on the discipline dropdown nearly shipped.
End-to-endThe full loop across both clients and the API: register → create → attach → submit → officer evaluates → assessment issued → applicant pays → officer verifies → permit generated → released. Run against staging per release.
Non-functionalAccessibility, performance budgets, and security scanning as pipeline gates, not as periodic projects.

Determinism rules, learned here

  • Pin the clock in any test whose outcome depends on a date. On 19 August 2026 the mobile suite failed because professionals_screen read the wall clock while its test pinned the provider's, so an assertion of "expires in 44 days" decayed by one day, every day. The screens now read the provider's clock and the test is the regression guard.
  • Run CI at varied times of day, or pin the clock. Quiet hours are 21:00–07:00; an unpinned notification test passes in the morning and fails at night.
  • Add an architecture test that fails on DateTime.now() in presentation code. The two defects found by this sweep were the same defect twice; a lint is cheaper than finding it a third time.
  • No sleeps, no network, no shared mutable fixtures. A flaky test that is retried is a test nobody believes.

Pipeline gates

every pull request     format · analyze/lint · unit · widget/component ·
                       contract (consumer) · SAST · secret scan · SCA
merge to main          all of the above · integration · contract (provider) ·
                       build artefacts · SBOM · deploy to staging
release                e2e on staging · performance budgets · accessibility ·
                       DAST · manual approval · deploy to production ·
                       smoke tests · automatic rollback on failure

Acceptance criteria

  • All three repositories have CI running on every pull request, with required status checks that cannot be bypassed.
  • A breaking API change fails provider contract verification before any client is affected; proven by a deliberate break.
  • The end-to-end journey runs green against staging on every release candidate.
  • An architecture test fails the build on a wall-clock read in presentation code.
  • The suite is proven deterministic: 50 consecutive runs, at different times of day, all green.
  • Coverage is measured and reported per repository, with agreed thresholds on domain logic specifically rather than on the codebase as an average.
  • DORA metrics are collected: deployment frequency, lead time, change failure rate, restore time.

F   Definition of done, for the programme

The programme is complete when all of the following are true at once.

  • An applicant registers, files a permit application, attaches documents, receives an assessment, pays, and receives a permit — entirely through the mobile app, against the production backend.
  • An LGU officer receives that application, verifies its documents, evaluates it, issues an Order of Payment, verifies payment, approves, generates and releases the permit — entirely through the web admin, against the same backend.
  • Both applications display the same record, in their own vocabulary, from one authoritative source, with no client computing a status the server owns.
  • Every action either party took is in a tamper-evident audit trail, attributable and timestamped.
  • Processing time is measured against the LGU's published Citizen's Charter, with suspension while the applicant is responding, and is reportable to ARTA.
  • An independent penetration test has been completed and no high or critical finding remains open.
  • The system is registered with the NPC, has a reachable DPO, and every data subject right is exercisable in-product.
  • Continuous integration runs on all three repositories and a contract break fails the build before it reaches a client.
  • Service level objectives are published, monitored, and met; alerts have runbooks that have been used in a drill.
  • A restore from backup and a rollback have both been rehearsed, timed, and recorded.
  • The LGU can operate the system without the team that built it.
One measure above all others. The system is finished when an applicant who files a permit on their phone and an officer who decides it in the office are, demonstrably and auditably, looking at the same record. Everything in this document exists to make that sentence true.
